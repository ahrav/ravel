## Architecture

Grant issuance sits between two already-shipped planes that do not currently touch:

1. **Object plane (S3).** `scope.rs` derives deterministic keys from `ScopeIdentity`/`WorkRef`;
   `storage/s3.rs` performs `put_if_absent`/`put_if_match`/`get_object` and classifies ambiguity into
   `MutationOutcome`; `distributed/claims.rs` is the read-only codec+intake for one such durable record.
   A grant record is the same shape of thing as a claim: a bounded JSON object at a deterministic key with
   a `record` discriminator, decoded only against expected bindings. Nothing in `claims.rs` writes, so the
   issuance side has to compose `s3::put_if_absent` + a new grant `intake`-shaped read-back itself; the
   only in-repo precedent for reconciling an ambiguous `put_if_absent` is
   `S3Store::publish_with_history` (`s3.rs:318`), which resolves via `verify_object` on the digest, not
   via an operation-identity comparison.

2. **Projection plane (SQLite).** `sync/head.rs::append_plan_admitted` publishes plan bytes → event →
   head; the head is the only carrier of `active_plan_digest`. `db/projections.rs::apply_scope_event`
   folds a `ScopeProjectionPayload::PlanAdmitted { plan_digest, proposal }` in **one transaction** that
   calls `admit_plan` → `insert_work_row` per `WorkSpec` (recording `max_attempts` and `deadline_unix_ms`)
   and then `ADMIT_PLAN_SQL` (recording `scopes.reserved_budget_units`). `admitted_work.grant_fence` is
   already the durable "a grant exists for this exact claim generation" bit, and `RESUMABLE_WORK_SQL`
   already refuses to resume unless `grant_fence = claim_fence`.

3. **Authority.** `ControllerAuthority` is unforgeable-by-construction (private fields, no `Clone`, only
   `scope_controller::acquire`/`renew` produce it). It carries the exact `ObservedScopeHead`, so
   `authority.head().active_plan_digest()` is both "the admitted plan" and "proven current at the last
   fenced observation." `into_parent`/`stop` consume it, which is the crate's existing way of making a
   mutation authority single-use.

The gap this bead fills: there is no grant *record* (only the `grant_fence` bit), no key for one, no
issuance function, no use-side validator, and no unit/attempt ledger. `scopes.reserved_budget_units` is
written but read by nothing; `admitted_work.max_attempts` is written and read only by nothing (only
`deadline_unix_ms` is read, by `READY_WORK_SQL`/`RESUMABLE_WORK_SQL`).

Wiring the pieces: `src/distributed.rs` (4 lines) must gain `pub mod grants;`. `src/scope.rs` gains
`scope_grant_key` beside `scope_claim_key` and `tests/wire.rs:197` gains its literal assertion. Any new
SQL constant must be added to the `apply_lookup_statements_avoid_table_scans` plan list
(`projections.rs:1471`); any new table must be added to `TABLES` (`:36`) and `SCHEMA` (`:146`), because
`validate` compares `sqlite_master` count and normalized DDL against them (`:1156`, `:1223-1234`).

**Hard constraints observed in-tree, not just asserted by the task:**
- All deps in `Cargo.toml` are `=`-pinned; the only serialization crates available are `serde`,
  `serde_json`, `ciborium`. JSON is `serde_json`, matching `claims.rs`/`head`.
- `ApplyError` has exactly four variants and rowcount-0 → `Conflict` is the universal idiom.
- `stored_u64` is the single u64→i64 boundary; anything above `MAX_STORED_INTEGER` cannot be stored.
- `DbHandle` gives one connection per command; there is no cross-command transaction today.

## Open Questions / Risks (facts that bear on the unknowns)

1. **`scope_grant_key` contradicts a documented rule.** `src/scope.rs:598-603` states the claim key
   deliberately excludes `claim_fence` so a reader that has not seen the record can address it. Putting
   `claim_fence` in the grant key makes the key unaddressable-before-read, which is exactly what
   AC4 reconciliation ("read the key back") needs to *not* be true unless the issuer already knows the
   fence. The issuer does know it (it issued for that fence), so this is resolvable — but it is a stated
   divergence from the sibling key, not a mirror.
2. **No cumulative-units column exists.** `scopes.reserved_budget_units` is the ceiling; there is no
   consumed-units column and no attempt counter. `admitted_work` has `max_attempts` but nothing counts
   attempts. Any "consume the reservation" predicate needs a **new column or table**, which trips
   `TABLES`/`SCHEMA`/`validate` and the query-plan gate.
3. **No cross-command transaction boundary.** `DbHandle` serves one command per `&Connection`
   (`worker.rs:481-620`). Making "check reservation + decrement + set `grant_fence`" atomic requires either
   one new `Command` variant that opens its own `transaction()` (the `apply_scope_event`/`admit_plan`
   pattern) or a single conditional `UPDATE` that does all of it. `RECORD_GRANT_SQL` alone cannot.
4. **`RECORD_GRANT_SQL` is a bit, not a ledger.** It sets `grant_fence = ?4` unconditionally when
   `claim_fence = ?4` and no terminal digest. It records no units, no attempt, no grant digest, and is
   idempotent-by-overwrite (re-running it succeeds), so it cannot by itself bound cumulative consumption.
5. **"Revoked" has no durable representation.** Nothing in the schema or docs defines revocation.
   `docs/mvp-outline.md:1080-1084` explicitly calls "the rule that makes a grant unusable after claim
   reclamation" an open contract question, and `docs/epics.md:229` treats cancellation as separate from
   supersession ("preserves existing effect deadlines"). Supersession-by-fence is what
   `RESUMABLE_WORK_SQL`'s `grant_fence = claim_fence` already implements; whether that alone satisfies
   the governing docs is genuinely unsettled in-tree.
6. **`ControllerAuthority` currency is observation-time, not issuance-time.** `head()` returns the head
   read at `acquire`/`renew`. Only `must_stop(now_ms)` bounds staleness. There is no in-crate way to
   re-prove currency without a fresh `read` or a `commit`, and `into_parent`/`stop` consume the value.
7. **No production caller of `append_plan_admitted` exists** (only `src/sync/head.rs:2185, 2236, 2253`
   tests). So "issuance obtains the admitted plan/work/claim state" has no production plan-admission
   caller to hang off yet, and the b8d.2 ledger explicitly defers the pre-gating obligation to this bead
   and `ravel-e1n.1`.
8. **No `ActorId`/`InstanceId` on the projection.** `admitted_work` records fences and leases but not
   owner identity; claim ownership identity lives only in the S3 claim record. A grant validator that
   wants "matching durable bindings" must decide whether it reads the claim object too (`claims::intake`)
   or trusts `admitted_work.claim_fence` alone.
9. **`ProposalError` has no grant-shaped variant** (`BudgetOutOfRange` is the closest). A new flat error
   enum in `grants.rs` is the convention (`WireError`, `ClaimRejection`, `ApplyError`, `AuthorityError`,
   `ProposalError` are all module-local flat enums with static `Display` text and `impl Error`).
10. **Adding SQL silently breaks a gate if forgotten.** `apply_lookup_statements_avoid_table_scans`
    (`projections.rs:1471`) enumerates constants by name; a new constant not listed there is untested
    for table scans, and a new table not in `TABLES` fails `validate` with `ValidateError::InvalidSchema`.
